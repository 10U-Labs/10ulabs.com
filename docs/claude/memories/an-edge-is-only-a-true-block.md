# An edge is only a true block

A `blocked_by` edge says one thing: this issue cannot be finished until that one is. It is written where that is true and left off where it is not. An issue that nothing waits on is filed with no edge at all, and that is a finished placement rather than a missing one — it is worked by number like every other unblocked issue.

The rule replaces an earlier one that always wrote an edge. That one had a third case: where the new issue blocked nothing, it was given an edge onto the tail of the queue, the one open issue nothing else was blocked by, so that every filed issue had a position. The intent was that nothing filed could be forgotten. What it produced was a queue whose edges could not be read, because a reader has no way to tell an edge that records a dependency from an edge that records an arrival time.

The cost was measured on 2026-08-23. Fifteen `blocked_by` edges were written across the twelve open issues, and eight of them said nothing true. Counted by reading each issue in full and asking of each edge whether the waiting issue's own `Proposed Solution` could land green with the blocker not done. Four of the eight were a single chain — #574 to #575 to #576 to #577 — of four issues with no dependency anywhere in it: a sessions state rewrite, a `mypy` flag in nine workflow files, a bootstrap refactor of a shared helper, and a new script under `scripts/`. Each pair touches different files for different reasons. #560, the retry handler's dead `2xx` branches under `src/api/endpoints/github_workflows/`, waited on #567, five unrequested pytest fixtures in `lib/python/test_fixtures/unit.py`, which is as unrelated as two issues in one repository get.

The chain also hid the one real block it was standing in for. #577 says in its own last paragraph that it has to come after #574, "In the other order the step goes red on the tests #574 is already deleting" — a genuine dependency, and the edge on #577 pointed at #576 instead. An edge written for position does not merely add noise; it occupies the slot the true edge would have used, and the true one is then never written because the issue already has one.

Decide by reading rather than by feel. Ask whether the waiting issue's `Proposed Solution` can land green with the other one not done. Two answers settle almost every case. A solution that already carries the contingency — #567 says of a fixture belonging to #565, "if either is still present when this is picked up, delete it here and say so in the commit" — has answered against itself: it is finishable in either order, so it takes no edge, whatever the prose around it says about queue position. A solution that would land red takes one: #559 installs a check that reports 42 definitions today and lists 37, the difference being the five `aws_clients` functions #585 deletes, so #559 cannot go first. So does a solution that names a job, a flag or a file the other issue creates: #586 adds a workflow job slotted against `assert-no-unused-python-definition`, which does not exist until #559 lands.

Overlap is not dependency. #565 and #559 both delete from `lib/python/test_fixtures/unit.py`, and each names the other and says who owns which lines. Two issues can touch one file, in either order, and neither blocks the other; what makes a block is that the work cannot be completed, not that it would be tidier afterwards.

What the old rule was protecting against is worth keeping in view. An issue filed in another repository is reached by the autopilot traversal only by following an edge into it, so one with no edge is never picked up there. The answer is not a false edge: work that belongs in another repository is filed as an issue here, naming that repository in its `Proposed Solution`, which is what #586 does for the tool it changes. Within this repository nothing is lost, because the pick is the lowest-numbered unblocked issue and every filed issue has a number.
